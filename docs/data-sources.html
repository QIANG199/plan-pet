PlanPet Internals · 2026-08

数据从哪来：额度、事件与桌宠动画的实现原理

Z.ai 与 Cursor 都没有公开发布"套餐用量 API"。本项目借用了三个现成的东西——官方控制台自己的监控接口、本机登录态、编辑器的 hooks 扩展点。这份文档讲清每条链路怎么走，以及两个高频疑问：额度查的是谁、事件为什么会有断档。

GLM 额度 · 半官方接口

  • GET api.z.ai/api/monitor/usage/quota/limit
  • z.ai 控制台用量页前端自己调的 XHR
  • 用你自己的 API Key 查你自己的账户——最稳的一条
  • 路径未公开文档化，字段按社区验证硬编码

Cursor 额度 · 登录态模拟浏览器

  • 读本机 Cursor 的 SQLite（state.vscdb）取会话 Cookie
  • 替浏览器去问 cursor.com 用量页私有接口
  • 三条链路里最脆弱：客户端升级 / 上游改版就断
  • 失败只影响单卡显示 fail，不牵连其他

桌宠事件 · 官方 hooks 扩展点

  • Cursor / ZCode 都正式提供进程钩子机制
  • 生命周期回调转成本地 HTTP 推送
  • 无逆向、无注入——所以远比额度链路可靠

Section 01 · Overview

数据链路总览

实线全部为本地回环或本机直连；中转服务是唯一同时接触上游与面板的角色。

关键认识：面板不是在轮询 z.ai 或 Cursor。中转服务每 5 分钟向上游拉一次额度缓存在内存；ESP32 每秒轮询的只是这台服务的内存快照（GET /api/dashboard）。所以额度是分钟级新鲜度，桌宠状态才是秒级实时——两条不同频率的时钟在同一次快照里交汇。

Section 02 · GLM Quota

GLM 额度：控制台同款监控接口

实现在 server/src/glm.js（约 60 行），无任何依赖，就是一次带认证头的 fetch。这个接口是 z.ai 编码套餐控制台用量页在前端里自己调用的 XHR——发现方式就是开 DevTools 抄请求。它要求 API Key 认证，本质上是"用你自己账户的身份查你自己账户的监控数据"。但注意：它不在任何官方 API 文档里，路径与响应结构随时可能变，代码按社区已验证写法硬编码（字段映射参考 cc-switch #1588，见设计方案 §4.1）。

响应字段取舍
limits[].type = TOKENS_LIMIT唯一采用的类型；TIME_LIMIT 是 MCP 月度次数，面板不做，直接过滤
unit=3, number=5判定为 5 小时窗口 → 屏上第一条进度条 + 行内倒计时
unit=6, number=7判定为 7 天窗口 → 第二条；老套餐没有此条则该条不画（week=null）
匹配不上 unit/number 时按 nextResetTime 升序兜底：最短窗当 5h、次短当周窗（pickWindows(), glm.js:12）
percentage / nextResetTime进度条值 + 重置倒计时，仅此两字段被消费；currentValue / remaining 一律不读，把对上游结构的依赖面压到最小

刷新节奏由 server/src/index.js:229 控制：启动立刻拉一次，之后每 5 分钟定时拉。成功整体覆盖内存缓存；失败写成 { ok:false } 打日志，下个周期再试——不做退避，因为频率低到没必要。

区域边界：国际版 z.ai vs 国内 bigmodel（重要）

结论先行：额度查询与 ZCode 毫无数据通道。接口查的是「你出示的那把 API Key 对应账户，在该域名下的编码套餐」的服务端真实用量。ZCode 只是另一个 HTTP 客户端，它连哪个 base URL、用哪把 Key，中转服务的查询完全感知不到。

如果不做任何处理就把 ZCode 从国际版切到国内 bigmodel 编码套餐，会出现危险的错位：面板继续按默认的国际版域名查询，展示旧套餐的用量，而真实消耗发生在新账户上——数字系统性偏离现实。为此额度模块已内置区域切换（实现位于 server/src/glm.js 的 monitorUrl() / Bearer 自动回退，环境变量经 env.js 注入），切换只动 .env：

步骤操作
换域名.env 加一行 ZAI_API_BASE=https://open.bigmodel.cn（缺省即国际版 api.z.ai）。同一条监控路由换 host（社区口径见 CodexBar），国内同为 5 小时窗 + 周限制机制；首次切换后看一眼卡片数值是否合理即可
换 KeyZAI_API_KEY 换成 bigmodel 平台签发的 Key；两区域的域名与 Key 不跨域通用
认证前缀 · 零配置自动回退已内置：每次先按裸 key 发出，遇到 401/403 自动补 Bearer 前缀重试一次。国际版实测裸 key 直通；国内版无论哪种写法可通都能命中，无需再人工分辨

改完 .env 重启中转服务生效。智谱官方为国内版另提供正规用量插件 glm-plan-usage（npx @z_ai/coding-helper），可作为对照参考。

Sources: docs.bigmodel.cn/cn/coding-plan/faq · github.com/steipete/CodexBar/blob/main/docs/zai.md · zcode.z.ai/en/docs/configuration

Section 03 · Cursor Quota

Cursor 额度：读本机登录态，替浏览器去问

cursor.com/dashboard 的用量接口用 WorkOS 会话 Cookie 认证，而这份登录态存在本机 Cursor 客户端的 SQLite 里。所以 server/src/cursor.js 分两步走：

步骤细节
① 读登录态
vscdbPath() / readSession()		打开 %APPDATA%\Cursor\User\globalStorage\state.vscdb（VS Code 式 ItemTable KV 库），取 cursorAuth/accessToken 与 adminSettings.cachedAuthId。两个都要——实测只带 accessToken 会 401。先 copyFileSync 到临时目录再只读打开（运行中被锁/WAL 问题）；用 Node 内置 node:sqlite 零第三方依赖
② 模拟浏览器调用
fetchQuota()		GET https://cursor.com/api/usage-summary，Cookie 形如 WorkosCursorSessionToken={cachedAuthId}::{accessToken}，附带 Origin/Referer 头伪装成 Dashboard 页自身的 XHR——带上完整两段式 Cookie 后服务端无法区分脚本与真浏览器

字段映射同样克制：membershipType 进卡片副标题，billingCycleStart/End 算账期倒计时，进度条只用 individualUsage.plan.autoPercentUsed（屏上 composer & grok 条）和 apiPercentUsed（other 条）。禁止拿 used/limit 自行相除；on-demand、aggregated events 等上游一大堆结构全部不碰。

这是三条链路中最脆弱的一条：同时依赖客户端存储路径与非公开 Web 接口。方案探索致谢社区同类项目 github.com/FreePeak/cursor-usage 与 github.com/lixwen/cursor-usage-monitor（完整清单见 docs/credits.md）。

Section 04 · Events → Pet States

六个 hooks 事件如何变成六种表情

先纠正一个直觉：动画状态不是从事件名逐个翻译来的。hooks 是编辑器提供的生命周期采样点，它们本身就是"全部能观测到的东西"。服务端 pet.js 把事件流喂进一个小型状态机，靠三类规则推导出表情：进行态信号（UserPromptSubmit / PreToolUse → thinking）、终止信号（Stop → happy 或 error；PostToolUseFailure → error）、以及静默推导（typing 十秒无后续自动收敛 happy 再归 idle；全局 15 分钟无声则 sleeping）。

pet.js 泳道参数：HAPPY_MS = 4s · SETTLE_MS = 10s · SLEEP_MS = 15min；tick 每 30s 巡检一次。

单轮对话的时间线：事件打点 vs 状态保持

下面这张时间线回答"间隙会不会造成 idle"：两个事件之间的生成段（模型在写下一个动作）没有任何事件上报，但泳道不会掉回 idle——busy 是粘性的，直到终止信号或兜底计时器到来。正常运行的一轮对话里不存在"干着干着变 idle"的空档。

E1–E5 为普通事件（ink/muted 圆点）；Stop 为唯一终止信号（coral）。思考题答案写在下一节。

Section 05 · Blind Spots

"Agent 在干活，桌宠却 idle"——什么时候会发生

直接回答：你的猜测部分成立，但不在最容易怀疑的地方。正常回合内的映射没有缝隙（上一节的时间线已经说明：间隙靠"busy 保持"机制覆盖，而不是靠补事件）。真正的断档来自以下五个场景，前两个占实际案例的绝大多数：

场景机制表现与对策
① 钩子失联 Cursor 大版本更新清空 ~/.cursor/hooks.json（本项目 git 历史里就有专门修复）、安装不全、node 路径失效；或 npm start 没在跑/重启过，POST 全部静默失败（common.js 吞错误是刻意设计） 对应 lane 永久 idle，额度卡绿点同时熄灭且长时间纹丝不动。对策：node hooks/install.js status，缺了重装即可修复
② 事件面之外的工作 Cursor 云端/后台代理（远程跑）、网页版会话、或其他没注册适配器的工具 本地进程钩子天然收不到，设计边界而非 bug。表现同①但属于预期行为
③ 回合中途夭折 Agent 在 PreToolUse 之后、Stop 之前崩溃/被杀（Ctrl+C、关窗口）。typing 有 10s 兜底会收敛成 happy；thinking 没有兜底定时器（故意不加：纯长回答合法超过十秒，强行结算反而会在正常生成中途误报 happy） 前者表现为"没收尾就来了一下 happy"；后者会一直卡在 thinking 直到该 lane 下一个事件。可选改造：给 thinking 加长窗兜底（分钟级而非 10 秒级）
④ 长生成段的瞬闪 两次工具调用之间生成超过 10 秒，typing 兜底误判为 happy；紧接着的下一次 preToolUse 又把它拉回 thinking 视觉上闪一下 happy 再回 idle、下一次 preToolUse 到来才恢复 thinking——这正是「happy 之后转 idle」的高频来源。无害抖动，但频繁出现说明本机工作负载的生成段普遍长于 10 秒
⑤ 双代理择优错觉 动画同一时刻只跟一个"当前代理"：ZCode busy 时永远优先，即使 Cursor 同时也在干活 不是断档而是优先级规则。各自的绿点（dots）独立点亮——看 dots 而不是动画就能同时看到两边活性
排查口诀：桌宠 idle 且绿点灭有两种成因——若此前刚闪过 happy、稍后又随新事件回到忙态，那是场景④的静默误判而非断链；只有整段时间完全纹丝不动才是钩子失联（场景①，重装即愈）。绿点亮着而动画不理 → 择优规则让位给了另一边（场景⑤）。

凭证边界与断链排查

凭证存哪用途与归属

WorkosCursorSessionTokenCursor 自己的 vscdb，只读不存本机 Cursor 登录态两段式 Cookie，usage-summary 认证
